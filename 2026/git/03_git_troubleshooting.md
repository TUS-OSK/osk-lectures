# 逆境編：よくある失敗とトラブルシューティング

Git を使っていると、必ずと言っていいほど「やってしまった！」という場面に遭遇します。この資料では、初心者が陥りやすい失敗と、その解決方法を学びます。

---

## 🚫 これだけはやってはいけない！ 3 つの禁忌

### 1. 巨大なファイルや実行ファイルを push する
`a.out` や `main.exe`、あるいは数GBあるデータセットなどを GitHub に上げてはいけません。
- **理由**: GitHub のリポジトリが肥大化し、クローンやプッシュが非常に遅くなります。一度 push してしまうと、履歴から消すのが大変です。
- **対策**: 後述の `.gitignore` を必ず設定しましょう。

### 2. 秘密情報（パスワード・API キー）を push する
設定ファイルに書いたパスワードなどをそのまま GitHub に上げてはいけません。
- **理由**: 公開リポジトリ（Public）の場合、世界中の誰でも（そして悪意のあるプログラムも）それを見ることができてしまいます。
- **対策**: `.env` などの設定ファイルを `.gitignore` に追加するか、GitHub の「Secrets」という機能を使いましょう。

### 3. チーム開発での強制プッシュ (`push -f`)
自分のローカルの履歴でリモート（GitHub）を無理やり上書きするコマンドです。
- **理由**: 他の人が push した変更を跡形もなく消し去ってしまう可能性があります。チームが崩壊します。
- **対策**: 自分の個人ブランチ以外では絶対に使わないでください。

---

## 🛠️ 「困った！」時の処方箋

### ケース1：余計なファイルを push してしまった
「あ、`a.out` も一緒に push しちゃった！」という場合。

1. **まずは `.gitignore` に追記**して、今後追跡されないようにします。
2. **Git の管理対象からだけ外す**コマンドを打ちます（ファイル自体は消えません）。
   ```bash
   git rm --cached a.out
   git commit -m "a.outを管理対象から外した"
   git push origin <ブランチ名>
   ```

### ケース2：マージ中に訳が分からなくなった
コンフリクトを直そうとしたけど、ぐちゃぐちゃになって最初からやり直したい時。
```bash
git merge --abort
```
これで「マージを開始する前の状態」に安全に戻れます。

### ケース3：`detached HEAD` と表示された
ブランチ名ではなく、古いコミットハッシュを指定して `checkout` した時などに起こります。「ブランチという枝から離れて、宙ぶらりんになった状態」です。
- **解決策**: 迷わず元のブランチに戻りましょう。
  ```bash
  git checkout main
  ```

### ケース4：操作ミスでファイルを消した / 編集しすぎた
「保存してないのに中身を消しちゃった！」という時。
```bash
git restore <ファイル名>
```
これで、最後にコミットした時の状態までファイルを復元できます。

## 💡 アドバイス

> [!IMPORTANT]
> **「壊した」と思っても、Git の履歴がある限り大抵のことは元に戻せます。**
> 
> 焦って適当なコマンドを連発するのが一番危険です。エラーメッセージをコピーして検索するか、詳しい人に「今の状態」を伝えて相談しましょう。
