# 応用編：チーム開発とコンフリクト解消

これまでは自分一人で作業する流れを学びましたが、実際の開発では複数人で同じプロジェクトを編集します。この資料では、チーム開発の基本ルールと、初心者が最も驚きやすい「コンフリクト（衝突）」の解決方法を学びます。

---

## 🌿 ブランチ（Branch）を活用する

チーム開発では、いきなり `main`（本番用）のコードを直接書き換えることはしません。
代わりに「**ブランチ（枝）**」を作って、自分の作業を独立させます。

### 1. 新しいブランチを作る
作業を始める前に、自分の名前や作業内容を付けたブランチを作ります。
```bash
git checkout -b feature-task1
```
（`checkout -b` は、新しい枝を作ってそこに移動するという意味です）

### 2. 作業してプッシュする
いつものように `add` と `commit` をした後、プッシュする時にブランチ名を指定します。
```bash
git push origin feature-task1
```

### 3. プルリクエスト（PR）を出す
GitHub 上で **Compare & pull request** というボタンが出るので、それを押して「自分の変更を main に取り込んでください！」とお願い（Pull Request）を出します。

---

## 💥 コンフリクト（競合）とは？

「同じファイルの同じ行」を 2 人以上の人が同時に書き換えてしまった時に発生します。Git は「どちらの変更を優先すればいいか分からない！」とエラーを出します。これが**コンフリクト**です。

### よくある場面
1. A さんが `main.cpp` の 5 行目を書き換えてマージした。
2. B さんも自分のブランチで `main.cpp` の 5 行目を書き換えていた。
3. B さんがプルリクエストを出そうとすると、「コンフリクトしています」と怒られる。

---

## 🛠️ コンフリクトの解消手順

もしコンフリクトが起きたら、以下のステップで解決しましょう。焦らなくて大丈夫です！

### 1. ローカルの `main` を最新にする
まず、A さん（他人）がマージした最新の状態を自分の PC に持ってきます。
```bash
git checkout main
git pull origin main
```

### 2. 自分のブランチに `main` を取り込む
自分の作業ブランチ（ここでは `feature-task1` とします）に戻り、最新の `main` を合体させます。
```bash
git checkout feature-task1
git merge main
```
ここで `CONFLICT (content): Merge conflict in main.cpp` のようなメッセージが出ます。

### 3. エディタで修正する
コンフリクトしたファイルをエディタで開くと、以下のような記号が出ています。
```cpp
<<<<<<< HEAD
自分の書いたコード
=======
最新の main にあったコード（Aさんの変更など）
>>>>>>> main
```
これを手動で書き換えて、**「最終的にどうなってほしいか」の形に整えます**（記号は消します）。

### 4. 解消したことを報告してプッシュする
修正が終わったら、いつもの 3 ステップ（の最後）を行い、再度プッシュします。
```bash
git add .
git commit -m "コンフリクト解消"
git push origin feature-task1
```

これで GitHub 上の警告が消え、無事にマージできるようになります！

---

## 💡 アドバイス

> [!NOTE]
> **コンフリクトは「エラー」ではなく「確認」です。**
> 
> Git が勝手にどちらかを消すのではなく、「どっちが正しいか教えて！」と聞いてくれているだけなので、落ち着いてコードを読み直せば必ず解決できます。
> 
> また、こまめに `main` から `merge` して最新を取り込んでおくと、コンフリクトを最小限に抑えることができます。
